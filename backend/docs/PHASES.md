# PHASES — план реализации бэкенда с Claude Code

Бэкенд делается по этапам. Один этап = одна сессия Claude Code = один PR.
Порядок выбран так, чтобы самая важная логика (проверки и решение) появилась рано
и была покрыта тестами раньше, чем на неё начнут опираться API и фронтенд.

Документы: `CLAUDE.md` (правила), `docs/SCOPE.md` (требования), `docs/BACKEND_SPEC.md` (архитектура), `docs/API.md` (контракт).

## Как проходить каждый этап

1. Новая сессия (или `/clear` после предыдущего этапа).
2. Включить режим планирования и вставить промпт этапа из этого файла.
3. Прочитать план Claude: какие файлы, какие тесты, что вне рамок. Поправить план до того, как он начнёт писать код.
4. Выйти из режима планирования, дать реализовать.
5. Проверить критерии готовности этапа сами: запустить тесты, руками дернуть пару эндпоинтов.
6. Коммит и PR. Если Claude менял `docs/API.md`, сообщить фронтенду.

Скоринг пока заглушка, а источники только моки (см. «Временные ограничения» в `CLAUDE.md`).
Во всех e2e с этапа 5 скоринг подменяется `FixedScoringEngine`, поэтому сценарии SCOPE проходят целиком и без модели.

Общие правила для всех этапов (уже есть в `CLAUDE.md`, повторять не нужно):
зелёные `pytest`, `ruff check`, `ruff format --check`, `mypy app`; не трогать то, что не входит в этап;
противоречия со спецификацией не исправлять молча, а спрашивать.

## Этап 0. Каркас проекта

**Цель:** проект собирается и поднимается одной командой, есть всё для качества кода.

**Входит:** `pyproject.toml` с зависимостями из `CLAUDE.md`, структура пакетов из BACKEND_SPEC раздел 2 (пустые модули),
`Dockerfile` на `python:3.15-slim`, `docker-compose.yml` (`api`, `postgres`, `minio`, `minio-init`),
`.env.example` со всеми переменными из BACKEND_SPEC раздел 1, настройки (`pydantic-settings`),
Alembic с пустой первой миграцией, `GET /api/v1/health` (проверяет БД и S3), обработчик ошибок в формате `ErrorOut`,
CORS, конфиг ruff и mypy strict, pytest с одним тестом на `/health`, GitHub Actions (ruff, mypy, pytest).

**Не входит:** бизнес-логика, модели БД, авторизация.

**Готово, когда:** `docker compose up --build` поднимает все сервисы, `/health` отвечает `{"status":"ok","db":"ok","s3":"ok"}`,
бакеты `credit-files` и `credit-contracts` созданы, CI зелёный.

## Этап 11. Worker и RabbitMQ (C4, уровень 2)

**Цель:** `api` только принимает запросы и держит WebSocket, конвейер выполняет отдельный процесс `worker`,
задачи и события идут через RabbitMQ. Бизнес-правила SCOPE и существующие контракты API не меняются.

**Входит** (по шагам, каждый шаг отдельным коммитом с зелёными проверками):

1. Docker Compose: сервисы `rabbitmq` и `worker`, переменные `RABBITMQ_URL`, `WORKER_PREFETCH`,
   `RECONCILE_INTERVAL_SEC`, `PIPELINE_STALE_AFTER_SEC`, зависимость `aio-pika`, RabbitMQ в CI.
2. Очередь и worker: порты `TaskQueue` и `PipelineLock` вместо `TaskRunner`, `Application.pipeline_run_id`
   и миграция, топология `applications.process` с DLQ, `PipelineConsumer`, идемпотентный `PipelineOrchestrator.run`,
   `PipelineReconciler` вместо `recover()`, `ExpirationJob` переезжает в worker. Сбор данных при неответившем
   источнике: снимки `FAILED` и `SKIPPED`, стоп-факторы на `CheckingData` по имеющимся данным
   (BACKEND_SPEC, разделы 6 и 11).
3. События в WebSocket: `RabbitStatusPublisher` в обоих процессах, `EventSubscriber` в api,
   `WsConnectionManager.deliver`.
4. Отчёт аналитика только после сбора: `409 INVALID_STATUS` в `SUBMITTED` и `CHECKING`.
5. `POST /applications/findings` и `FindingsBuilder`.

**Не входит:** outbox, несколько экземпляров worker в compose, перенос этапа 1 (форма) в worker.

**Готово, когда:** `docker compose up` поднимает `api`, `worker`, `rabbitmq`, `postgres`, `minio`, и сценарий 1
проходит руками через фронт или HTTP; e2e всех пяти сценариев зелёные (api и обработчик worker в одном процессе,
in-memory очередь); повторная доставка той же задачи и задача со старым `run_id` не дублируют снимки,
проверки и переходы; заявка в `SUBMITTED` без задачи в очереди уходит в работу после reconciler;
интеграционные тесты aio-pika на настоящем RabbitMQ: ack после commit, битое сообщение в DLQ, событие доходит
через fanout; сломанный источник даёт отчёт с `FAILED` и данными остальных источников; сломанный ЕГРЮЛ даёт
`SKIPPED` у зависимых запросов; findings клиента без проверок и `409` до конца сбора.

```text
Этап 11 из docs/PHASES.md. Прочитай CLAUDE.md, docs/BACKEND_SPEC.md разделы 1, 2, 6, 10, 11, 13, 17
и docs/API.md разделы 2.4, 2.6, 4.4, 4.5. Перестрой бэкенд на api + worker + RabbitMQ по описанию этапа 11,
шаг за шагом. Домен и сервисы не знают про RabbitMQ: только порты TaskQueue и StatusPublisher, реализация
```

## Если что-то пошло не так

- Claude ушёл в сторону или переписывает лишнее: остановить, `/clear`, повторить промпт этапа с уточнением, что не трогать.
- Тест «не проходит, поэтому поправлю тест»: не соглашаться, если тест проверяет число или правило из SCOPE.
- Длинный этап не помещается в контекст: разделить на подэтапы (например, 5a заявки, 5b конвейер, 5c WebSocket)
  и делать каждый в своей сессии.
- Спецификация оказалась неудобной в реализации: пусть Claude предложит изменение в `docs/BACKEND_SPEC.md`
  отдельным сообщением, решение принимает команда.
