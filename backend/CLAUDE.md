# CLAUDE.md

Бэкенд «Умного кредитного кабинета предпринимателя» (хакатон Альфа-Банка, кредитный конвейер для МСБ).
Клиент подаёт заявку на кредит, бэкенд асинхронно (отдельный процесс worker через RabbitMQ) проверяет её по источникам, считает скоринг,
принимает решение, аналитик разбирает нестандартные случаи, клиент подписывает договор,
дальше живёт договор с операциями и эмуляцией времени.

## Документы (читать перед задачей)

- `docs/SCOPE.md` — продуктовые требования. Источник истины для бизнес-правил, чисел и сценариев. Не редактировать.
- `docs/BACKEND_SPEC.md` — архитектура: слои, классы, порты, статусы, конвейер, JWT, WebSocket, S3.
- `docs/API.md` — контракт с фронтендом: эндпоинты, тела запросов, ответы, ошибки, сообщения вебсокета.
- `docs/PHASES.md` — план реализации по этапам с критериями готовности.

Если код, спецификация и SCOPE расходятся: бизнес-правила и числа берутся из SCOPE,
архитектура и контракт API берутся из BACKEND_SPEC и API. Найденное противоречие не исправляй молча:
опиши его и спроси.

## Временные ограничения (действуют, пока не сказано иначе)

1. **Все внешние источники только моки.** ЕГРЮЛ/ЕГРИП, БКИ, обороты, ФНС и ГИР БО, ФССП, ЦБ, Росфинмониторинг,
   ЭП банка, проверка паспорта: только классы `Mock*Adapter` за доменными портами, данные из синтетики.
   Никаких HTTP-клиентов к реальным сервисам, никаких `httpx`/`requests` к внешним адресам, никаких ключей API.
   Интерфейсы портов проектируй так, чтобы реальную интеграцию потом можно было подставить без правок домена.

## Стек

- Python 3.15, FastAPI (+ python-multipart для загрузки выписок), Pydantic v2, SQLAlchemy 2 (async) + asyncpg, Alembic
- PostgreSQL 16, S3-совместимое хранилище (MinIO локально), aioboto3
- RabbitMQ 4.3 (очередь задач конвейера и обмен событий), клиент aio-pika
- PyJWT (HS256), argon2-cffi для паролей
- reportlab для PDF договоров (шрифт DejaVu Sans лежит в `app/infra/documents/fonts/`)
- pytest + pytest-asyncio + httpx, ruff, mypy (strict)
- uv: зависимости в `pyproject.toml`, версии зафиксированы в `uv.lock`
- Docker Compose: сервисы `api`, `worker` (тот же образ, `python -m app.worker`), `rabbitmq`, `postgres`, `minio`,
  `minio-init` (создаёт бакеты); MinIO из образов `pgsty/minio` и `pgsty/mc`, официальных больше нет

Если какая-то зависимость ещё не ставится на Python 3.15, не обходи это хаками:
сообщи, какая именно, и предложи временно 3.14 (решение фиксируется здесь).

## Команды

```bash
docker compose up --build                 # поднять всё
docker compose exec api alembic upgrade head
docker compose exec api python -m app.infra.mocks.seed   # тестовые учётки и 5 сценариев
docker compose logs -f worker             # конвейер, reconciler, истечение сроков
pytest -q                                 # все тесты
pytest -q tests/unit                      # быстрые тесты домена
pytest -q tests/e2e                       # сценарии SCOPE раздел 12
ruff check . && ruff format --check .
mypy app
```

Задача считается выполненной, только когда зелёные `pytest`, `ruff check`, `ruff format --check` и `mypy app`.

## Архитектура: правила, которые нельзя нарушать

Слои и направления зависимостей: `api -> application -> domain <- infra`.

Процессы (BACKEND_SPEC, раздел 1, схема C4 уровня 2):

- `api` принимает запросы и отвечает: JWT, этап 1 (форма), запись заявки в PostgreSQL, постановка задачи, WebSocket.
  Конвейер (этап CHECKING и дальше) и фоновые задачи в `api` не выполняются. К источникам `api` обращается только
  там, где контракт требует синхронного ответа (`/companies/get`, согласия, форма, паспорт, ЭП выписки).
- `worker` (`app/worker.py`) берёт задачу из `applications.process`, ходит во все источники, сохраняет собранное
  в PostgreSQL, делает проверки и решение, публикует события. Там же reconciler и `ExpirationJob`.
- Домен и сервисы не знают про RabbitMQ: очередь и события только через порты `TaskQueue` и `StatusPublisher`,
  реализации на aio-pika в `app/infra/messaging`.
- Обработка задачи идемпотентна: повторная доставка и задача со старым `pipeline_run_id` не дублируют данные.
  ack только после commit, битые сообщения уходят в DLQ.

- `app/domain` не импортирует FastAPI, SQLAlchemy, aioboto3, aio-pika, PyJWT, httpx и ничего из `app/infra`, `app/api`, `app/application`.
  Только стандартная библиотека и Pydantic (для value objects допускается dataclass).
- `app/application` зависит от доменных портов (абстрактных классов в `app/domain/ports.py`), а не от реализаций.
- Реализации портов живут в `app/infra` и связываются с портами только в `app/main.py` (composition root):
  `build_container` для api, `build_worker` для worker.
- Роутеры в `app/api/v1` не содержат бизнес-логики: принять DTO, взять `TokenClaims` из `Depends(current_user)`,
  вызвать сервис, вернуть DTO.
- Статус заявки меняется только через `ApplicationStateMachine.transition(...)` и методы `Application`.
  Прямое присваивание `app.status = ...` запрещено.
- События о смене статуса публикуются в `StatusPublisher` только после успешного `commit`.
- Новые стоп-факторы, факторы скоринга, триггеры ручной проверки и правила решения добавляются
  отдельными классами-наследниками и регистрируются в списке, а не через `if` в движке.
- Параметры продуктов берутся только из `app/infra/config/products.yaml`, не хардкодятся.

## Соглашения API

- Префикс `/api/v1`.
- Все параметры передаются в JSON-теле POST. Path- и query-параметров нет.
  GET только у эндпоинтов вообще без параметров (`/auth/me`, `/products`, `/dictionaries/*`, `/health`).
- `Authorization: Bearer <JWT>` обязателен везде, кроме `/auth/login`, `/auth/register`, `/health`.
- Идентификатор пользователя и роль никогда не принимаются из тела, только из расшифрованного токена.
- Статус заявки клиент получает по WebSocket `/ws/applications`, эндпоинта для опроса статуса нет.
- Ошибки всегда в формате `ErrorOut` с машинным `code` (список кодов в `docs/API.md`).
- Деньги: в коде `Decimal`, в JSON строка с двумя знаками (`"3600000.00"`). Ставки строкой (`"26.5"`).
- Даты `YYYY-MM-DD`, время ISO 8601 в UTC с `Z`.
- Имена полей в JSON `snake_case`, перечисления строками в `UPPER_SNAKE_CASE`.
- Файлы (выписки 1С, PDF договоров) хранятся в S3, клиенту отдаются presigned-ссылкой на 5 минут.

## Стиль кода

- Аннотации типов везде, mypy strict без `# type: ignore` (кроме сторонних библиотек без стабов, с комментарием почему).
- async во всём вводе-выводе. Синхронные блокирующие вызовы в обработчиках запрещены.
- Datetime только timezone-aware UTC. Текущее время только через порт `Clock`, не через `datetime.now()` в домене.
- Без `print`. Логирование через `logging` с `application_id` в контексте.
- Пиши код, который читается без комментариев. Комментарий нужен, когда объясняет «почему», а не «что».
- Имена классов и методов как в `docs/BACKEND_SPEC.md`, чтобы код можно было сверить со спецификацией.

## Тесты

- Каждое правило из SCOPE разделов 4, 5 и 6 (стоп-факторы, дозапрос, факторы скоринга, поводы ручной проверки,
  правила решения) покрыто unit-тестом на границах.
- Скоринг: `ScoringEngine` (10 факторов, классы A–D) из `app/domain/scoring/engine.py`. Антифрод-факторы
  (`client_visible=False`) клиенту не показываются. На синтетике сценариев SCOPE раздел 12 модель обязана
  давать эталонные баллы и класс (`tests/unit/domain/scoring/test_scope_scoring.py`).
- Класс C: `ClassCCounterOfferRule` пересчитывает скоринг и предлагает максимальную сумму или минимальный срок,
  при которых класс становится B или выше; если таких нет, заявка уходит аналитику.
- Пять сценариев из SCOPE раздел 12 оформлены e2e-тестами через HTTP и WebSocket. Скоринг в них подменяется
  `FixedScoringEngine`, который отдаёт баллы и класс из SCOPE раздел 12 для каждого ИНН.
  Ожидаемые классы, ставки и исходы берутся из SCOPE, их нельзя «подгонять» под код.
- Внешние источники в тестах это те же моки, что и в приложении, с синтетикой из `app/infra/mocks/data`.
- S3 в тестах: MinIO из docker compose или in-memory реализация `FileStoragePort`.
- RabbitMQ в тестах: e2e и тесты сервисов используют in-memory `TaskQueue` и шину событий из `tests/fakes`
  (обработчик worker работает в том же процессе). Адаптеры aio-pika проверяются интеграционными тестами
  на настоящем RabbitMQ (`TEST_RABBITMQ_URL`, по умолчанию из docker compose).

## Как работать

- Перед кодом покажи план: какие файлы создашь или изменишь и какие тесты напишешь.
- Работай в рамках текущего этапа из `docs/PHASES.md`, не забегай вперёд.
- Если меняешь контракт API или архитектуру, в том же изменении обнови `docs/API.md` или `docs/BACKEND_SPEC.md`
  и прямо скажи об этом в итоговом сообщении.
- Не добавляй зависимости, не перечисленные в стеке, без согласования.
- Не удаляй и не ослабляй существующие тесты, чтобы прошла сборка.
- Не коммить секреты. Конфигурация только через переменные окружения (`.env.example` держи актуальным).
